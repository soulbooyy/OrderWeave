# DeepSeek 重构后留出集 v1

本次交付为离线准备。6 道英文任务沿用既有真实模型实验的英文服务设置，使用新的用户原话和订单组合。输入文件只有匿名题号与用户轮次。评测者持有的金标另存，包含引用原文、任务类型、输出字段、直接依赖、条件来源、实际选中的分支、工具目标、预期值和业务末态。[输入](inputs.json) · [金标](gold.json)

| 题号 | 前一步如何影响后一步 | 必需角色与成功依据 |
|---|---|---|
| H01 / H02 | 同为“至少三件”，用 2 件和恰好 3 件的订单分别命中相反分支 | Billing 查数量后，Technical 只查选中的变体；答复须包含件数和正确规格。 |
| H03 | 先查咖啡机产品的变体清单，再与订单行匹配，最后查匹配项的颜色 | Technical → Billing → Technical；最后的变体编号由前驱推出。允许额外传递首个目录节点的结果给末节点。 |
| H04 | 商品变体清单和订单行可按任意顺序读取，查颜色需要两份结果的唯一交集 | Technical 与 Billing 各查一份记录，最后由 Technical 查匹配项；任一前驱缺失均不能得分。 |
| H05 / H06 | 先查头盔通风等级。低等级进入退货准备，其余等级只查订单状态 | Technical → Billing。H05 先解释依据并原样展示确认卡，第二轮确认后提交一次；H06 回复等级及订单状态，业务数据保持原状。 |

验收单位为 **6 道独立题**。完整计划共有 18 个金标节点、12 条必需直接边和 8 个带条件的节点，含未选分支。执行层只计实际适用的 14 个节点、8 条边。5 题应在第一轮完成，1 题必须等待确认。执行组每组 6 个会话、计划 7 个用户轮次。

## 下轮运行前约定

- 从相同哈希的零售种子各建独立库，使用服务端邮箱查找预先绑定该订单的所有者；初始化从计时轮次中排除。三组采用相同角色权限和实验映射 `order_lookup → billing`、`product_info → technical`，写入继续走业务确认守卫。
- 只测计划时，每题仅发送第一条原始用户消息，保留完整原始分类输出、实际版本、参数和契约拒绝原因。端到端从同一原始输入分别调用 `keyword`、`subintent`、`dag`，第一轮各题各组一次，轮换模式次序。H05 的第二条消息仅在出现有效确认卡后发送；此前没出卡或发生早提交通通记失败，保留在分母。不给角色或分类器投喂金标、后续用户消息、真实订单内容或此前另一组的结果。
- 同一轮对照锁定模型版本、语言、提示词、thinking、温度和输出上限。若结合本批计划输出改动提示词、语法、评分规则或运行器业务行为，本批移入调试集，新的泛化检验另行冻结。计划探针与端到端调用分别报告。
- 累计上限从 ¥5 提高至 **¥10**。冻结时既有实验账本 ¥4.93183652，本步新增 ¥0，可用 ¥5.06816348。后续付费运行读取本实验预算配置，从最新已结算额和未结算预留重新计算；分类、角色、汇总、重试和失败尝试都计入累计。端到端按整组三模式预留后开题；余额不足保留截断及原因。本次没有启动付费作业。[预算配置](budget.json) · [历史结算](../../RESULTS.md)

## 对齐和评分

1. **计划抽取。** 以任务类型、所问字段、字面目标或前驱派生目标、用户原文为锚，做一对一匹配。重复语义通过已唯一识别的父、子节点消歧；证据仍不足时报告歧义。模型节点名只连接同一计划内的引用。分开报告节点、边、条件的正确数／预测数／金标数，以及整图完全正确数／6 和生产契约拒绝原因。条件核对来源、完整原话与真假分支；阈值、比较符及类型由实际契约解析。H03 允许的冗余传递边单列，不计入必需边分母。纯子意图只评分解，关键词的抽取指标不适用。空计划、错边和被拒计划都保留在分母。
2. **角色与顺序。** 有原始计划时使用本地 ID 将尝试绑定到已对齐节点，再校验实际工具和目标；旧轨迹用工具、目标及可观测的请求字段对齐。歧义、缺派均不得分。规格任务按金标中的具体变体查询评分；只查产品大类不构成变体查询完成证据。角色分配按正确角色与目标计数；顺序要求带匹配字段值的成功前驱出现在后继尝试之前。独立前驱可互换。缺端点、无前驱证据、逆序、未选分支、重复、额外调用、预算截断分别统计。
3. **最终成功。** 全部适用任务须有权限范围内的工具证据；用户提出的结果全部送达，且订单、退货条目、退款去向、事件数、终态和挂起操作均符合金标。H05 只允许一次准备和一次次轮提交，以同一服务端 op_id 串联准备、已展示的原样确认卡、提交调用及唯一退货事件；确认前要求先说明已查等级与选择依据。只读题不允许确认卡或其他业务变更。正确等待与最终完成分开计。
4. **答复盲评。** 评审只看题面、应有事实、实际用户可见回复与确认卡界线，隐藏模式和节点名。记录 `requested_facts`、`no_contradiction`，H05/H06 另核 `selection_explained`，H05 再核 `basis_before_card`、`submission_acknowledged`。同义表达和数字拼写均可通过；疑问、引用条件或否定不能充当事实陈述。金标的正则只用于定位，不决定真实回答对错。缺盲评保留在分母，并标记待评。确认卡与业务证据仍由代码核对。
5. **成本与延迟。** 各阶段、各模式分别报实际输入／输出 token、缓存、请求数、人民币费用、每轮墙钟时间（含工具和重试）、P50/P95 及样本量。实际计费取运行时模型费率和账本。优先给逐题配对结果，单次小样本只用于诊断。

`grade_plan(case, rows, mode)` 接收真实分类器的原始节点列表。`grade_session(case, row, review)` 接收顺序记录的工具证据、发表的回复、实际用户轮次、服务端已展示卡、事件与独立数据库终态。DAG 有原始图时设置 `row.plan`，纯子意图设置 `plan_mode="subintent"`。额外业务变更计数来自前后快照，仅扣除金标允许的变更；操作号及展示事实从业务库读取。阶段三已发表的旧成绩与旧评分版本保留。
