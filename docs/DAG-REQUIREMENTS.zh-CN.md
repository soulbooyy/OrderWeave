# OrderWeave 零售 DAG 编排重构需求

状态为待实施。本文定义对外行为和验收口径，代码基线为 `4407724`。实施顺序、测试夹具与回退办法见 [TDD 路线图](DAG-ROADMAP.zh-CN.md)。

## 1. 目标与范围

用户提出多个相互依赖的诉求时，系统应在已有信息和授权允许的范围内，在同一轮完成所有已就绪的工作。只有目标不明确、缺少用户信息或业务要求新的确认时，才向用户索取输入。最终答复必须说明已查实什么、哪些诉求仍未解决。

本次改造作用于零售 `dag` 模式，覆盖 LangGraph 和 legacy 两个入口。默认路由继续使用 `keyword`，`subintent` 保留作对照。第一版串行执行就绪节点。角色能力、身份归属、写操作确认、预算和已有人工交接规则继续生效。并行执行、任意代码条件、自动生成工具以及更换模型均在本次范围之外。

当前规划器会把节点按角色分组，当前执行器仅为成功读单后的商品查询追加同轮调度，角色结果按角色名记录。改造后，同一角色可多次执行不同节点。以“查头盔变体 → 核对我买的变体 → 查该变体的通风等级”为例，在读单归 Billing 的实验配置下，三个节点依次由 Technical、Billing、Technical 执行，两次 Technical 的目标、证据和状态各自保留。[当前规划器](../core/retail_subtasks.py) · [当前编排器](../agents/agent_orchestrator.py) · [运行配置](../agents/retail_runtime.py)

## 2. 功能需求与验收条件

### R1　计划、节点与结果证据

计划具有稳定的 `plan_id`、契约版本和会话归属。节点在计划内以 `task_id` 唯一标识。保存用户原话引用、任务类型、必需依赖、可选条件、预期输出字段和目标约束。类型对应的可用能力、字段类型和证据要求由服务端定义。沿用现有 1 至 12 个节点、原话引用、重复 ID、未知前驱和环的校验。模型提取的工具名、角色或条件均不能授予权限。

每次执行记录计划、节点、轮次、尝试标识、实际执行者、状态、原因和证据引用。后继只接收所需的结构化事实。完成判定按任务类型进行：

| 任务 | 完成依据 |
| --- | --- |
| 订单或账务查询 | 绑定用户范围内的成功工具结果，与请求的订单和所需字段一致。要求唯一订单行时，多个候选须澄清。 |
| 商品或政策查询 | 目标商品或变体及所问属性匹配工具结果；政策类说明引用适用的规则或知识证据。查到其他变体、工具被拦截、仅有角色口头结论均不足以完成。 |
| 业务写入、身份绑定、人工交接 | 分别以匹配操作和参数的成功业务事件、服务端绑定状态、已记录的交接事件为准。生成待确认卡只证明已准备。 |

### R2　节点生命周期与调度

| 状态 | 进入条件与后续行为 |
| --- | --- |
| `pending` | 新节点，正在等待正常推进中的前驱。前驱都已完成后检查条件与权限。 |
| `ready` | 必需输入已验证、条件成立、存在具备能力的执行者。调度时原子领取为 `running`。 |
| `running` | 记录当前尝试；仅此尝试能提交结果。根据证据转为成功、失败、等待用户或待核对的阻塞状态。 |
| `succeeded` | 已满足 R1 的证据要求；可向后继公开限定字段。完成节点不重复派发。 |
| `waiting_user` | 需要身份信息、目标选择或下一轮真实确认。持久化等待原因及关联对象；新输入通过服务端核验后才允许同一节点再次就绪。 |
| `blocked` | 有明确障碍，如前驱失败或等待用户、缺少必需事实、没有合格执行者、写结果未知。记录原因和阻塞来源。可解除的障碍经核对后重新评估；失败前驱的后继保持阻塞。 |
| `failed` | 本次节点执行已确定失败，记录错误与已有证据；本轮不自动重试。独立分支可继续。 |
| `skipped` | 已验证条件为假，或所属互斥分支确定未选中。保留判定依据，不派 Agent，不计为遗漏或成功执行。 |

执行顺序为“核对业务边界 → 计算就绪集合 → 领取一个节点 → 调用角色 → 验证并持久化结果 → 重新计算”。多个节点就绪时稳定地按拓扑序及原计划顺序选取。每轮最多派发 `min(计划节点数, 12)` 次，每节点每轮最多一次。没有就绪节点、达到上限或预算停止时，记录停止原因并汇总实际进展。模型工具循环的轮数和调用预算单独受限。独立读取可以在其他读取失败后继续；新确认卡待展示、状态操作结果未知或已转人工时，本轮停止派发。

### R3　角色能力与业务授权

角色负责专业工作。Scheduler 从具备对应能力、当前可用的角色中选择执行者。任务可用工具是**角色白名单、任务白名单、运行模式白名单的交集**。工具列表展示和执行前 Hook 使用同一判断。角色提示词携带当前任务目标与权限。General 降级执行也必须重新通过相同判断。

Technical 的商品任务只获得适用的商品及知识只读工具；Billing 的订单查询任务只能查单；General 按配置承担一般处理；Escalation 的交接必须有相应的交接依据。当前普通 Technical 的只读集合还包含用户和订单查询，因此仅移除 `PrimaryOnlyHook` 会扩大实际可用范围。项目默认 owner 与实验的 `order_lookup → billing` 覆盖分别测试。[工具集合](../agents/retail_tools.py) · [角色工具筛选](../agents/retail_multi_agent.py) · [现有守卫](../agents/retail_hooks.py)

身份绑定须经现有服务端流程。写操作按原规则准备、原样展示确认详情，并在后续真实用户消息确认相同对象和参数后提交。用户改参数需重新准备和展示；取消或换单使旧授权失效。交接摘要、角色回复和检查点都不能代替确认。

### R4　受控条件与汇合

首版条件只读取已声明前驱的、已验证的具名输出。条件包含来源节点、白名单字段、枚举运算符和同类型常量。数量支持整数比较，枚举值可判等。解析时验证操作数、字段、依赖及用户原话中的阈值与目标；无法可靠表达的条件应澄清。禁止脚本、函数调用和任意属性访问。

例如，`t1.purchased_item_count >= 3` 为真时查鼠标，为假时查头盔。两条分支共用同一判定，服务端生成互补选择。数量为 2 和 3 时应各执行一个正确分支；缺字段、类型错误或读单失败时不能默认走“否则”。若退回关键词路由会丢失用户条件，应暂停相应节点并说明缺少的信息。独立分支汇合要求所有必需前驱成功。互斥分支汇合要求已选分支成功，且有证据证明其他分支未选中；普通必需依赖的 `skipped` 不能满足汇合。最终汇总可直接读取各分支状态。

### R5　跨轮持久化、恢复与去重

建议在现有 SQLite 库内增设独立的编排记录，由两个执行入口共用。保存版本化计划、节点状态、尝试、条件判定、最小输出和证据引用，关联会话、绑定用户、等待原因及 `op_id`。业务表仍是身份、订单、确认展示和成功事件的权威来源。LangGraph checkpoint 负责工作流位置，仅引用计划；legacy 从同一编排记录恢复。请求内的 `call` 和既有客服诉求清单各自保留原用途。[工作流恢复](../agents/retail_workflow.py) · [业务记录](../mcp_tools/retail_store.py)

恢复已等待的计划前，核对会话、身份、业务目标和本轮输入。用户继续原请求时复用计划；改目标时使受影响节点和旧授权失效，独立新问题不能被当成确认。取消时关闭对应计划或分支，记录取消原因。旧会话没有新契约版本时走兼容入口，不从角色摘要推断节点已完成。

同一计划节点、轮次的领取和状态更新需防并发重复。若业务提交后、节点记账前崩溃，重启后先按操作引用核对服务端事件，再补记成功；无法核实时保持 `blocked` 并显式报告。节点去重之外，业务层还要防止不同节点或重复请求对同一已提交操作二次写入。

### R6　回复、API 与轨迹

Composer 每轮收尾一次，读取原始诉求、全部适用节点的状态和可公开证据，并能区分条件跳过和任务遗漏。订单查得 2 件、规格查询失败时，答复应包含“订单有 2 件商品；暂时无法确认头盔的通风等级”。退货准备完成时，先说明查到的结果和选择依据，再原样展示确认详情。成功提交和成功交接的表述均须能回溯到业务记录。Composer 无模型时也须按相同规则生成确定性回复。[现有汇总](../agents/agent_orchestrator.py) · [回复校验](../agents/retail_response_guard.py)

对外区分本轮状态与整项任务成功。建议增加 `orchestration_mode`、`turn_status` 和按实际先后排列的 `task_runs`。等待确认可以是正确的本轮结果，端到端完成仍需后续成功事件。DAG 输出不回填虚构的主角色；原模式和旧回放继续支持原字段。API、前端和评测均能显示同一角色的多次调用。任务轨迹暴露节点及必要引用，避免传出完整私有订单或写入凭据。[API](../api/main.py) · [前端追踪](../web/src/components/TraceTree.tsx) · [旧评分器](../evaluation/harness/routing_ablation.py)

## 3. 三组评测口径

先用冻结任务图和脚本角色验证执行器，再用同一批用户任务、相同初始业务库副本、权限配置、模型与预算口径对比三种模式。留出题、可接受角色、条件分支、正确目标、必需边、用户确认点与成功断言均在运行前冻结。旧模式按相同的工具目标、业务事件及轮次对齐金标准节点；不能从旧轨迹可靠对齐的条目标记无法判定，并报告覆盖率。主辅误派指标只作旧模式诊断。

| 指标 | 计算与报告方式 |
| --- | --- |
| Task 分配准确率 | 正确角色执行且与目标匹配的金标准节点数 / 实际适用的必需节点数。缺派、无法对齐均不计正确，额外派发和重复派发另列。 |
| DAG 依赖顺序正确率 | 在前驱成功证据产生后才启动后继的金标准依赖边数 / 适用必需边数。列出缺端点、逆序和前驱未成功就执行的边；允许独立节点交换顺序。 |
| 同轮完成率 | 首次可执行轮内满足全部诉求的题数 / 已有全部信息和授权、应可同轮完成的题数。强制跨轮确认题另报正确等待率。 |
| 端到端成功率 | 用户全部适用诉求在规定轮数内得到正确答复，且所需业务事件已发生的会话数 / 计划评测会话数。部分完成、漏跑和预算截断分列，保留在分母。 |
| Token、费用与 P95 延迟 | 各组给出输入/输出 token、实际人民币费用、调用次数、轮端到端延迟 P95、样本数及预算截断数。区分系统、模拟用户与评审开销；离线时间不外推为真实模型延迟。 |

功能验收要求冻结的确定性用例逐项通过，越权调用成功、未经确认提交和重复写入均为零。真实模型的收益和开销需根据配对结果报告；本文不预设提升幅度，也不启动付费运行。
